haus is the design system every hipuku app is built on. A consumer takes two things from it, by
different routes: components, distributed as source through a [shadcn](https://ui.shadcn.com)
registry, and the design tokens underneath them, published on npm as `@hipuku/tokens` today and
`@hipuku/tokens` from the next release.

<GetStarted />

## Installing as source

A component you install is a copy in your own repository. Open the file, read it, restyle it,
delete the parts you do not need. When a behaviour fix lands here, `shadcn add` brings the new copy
and you merge it like any other change to your own code.

The tokens work the other way. They are a versioned package, because a value is not something a
product should fork: two apps whose `surface-raised` has drifted apart no longer look like one
company.

## Three decisions

Most of what is on this site follows from three choices. Each has a page that shows the values
rather than restating the claim.

**A component never names a value.** It names a role: the surface it sits on, the ink it writes
in, the border that is its edge. The same component is then correct in a light app, a dark one, and
in another brand. See [Colour](/docs/foundations/colour).

**A dark mode is the same mapping read again.** Every role carries a value per mode, resolved from
the theme on the document or the reader's system setting, so there is one mapping rather than a
light set and a dark set. See [Theming](/docs/foundations/theming).

**Contrast is tested.** `contrast.test.ts` in the token package holds every ink and surface pair
against WCAG AA in both modes, so a pair that would fail does not get released. See
[Quality](/docs/start/quality).

## Where to go next

[Install](/docs/start/install) is the registry entry and two lines of configuration. The
[foundations](/docs/foundations/colour) pages read their values from the page you are looking at,
in the mode you are in, so they show the system as it is rather than as it was documented.
